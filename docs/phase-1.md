# Phase 1 — Customer, Account and Ledger Foundation

## 1.1 Objective

Implement customer and account lifecycle APIs, establish the account balance projection and introduce the domain-level double-entry journal validator used by subsequent transfer processing.

## 1.2 Scope and invariants

- Customer email is trimmed and normalized to lowercase; PostgreSQL uniqueness is the final concurrency-safe guard.
- Account numbers are generated by the server. The caller cannot choose an account number, owner or opening balance.
- A new account starts with a zero balance and is ACTIVE only when opened for an ACTIVE customer.
- Account balance is a projection; callers cannot directly mutate it through the API.
- The journal validator requires at least two positive entries, a single currency per journal and equal total debits and credits.
- At this phase, API endpoints are not yet protected by the Phase 4 authentication layer. Do not expose the service to untrusted networks.

## 1.3 API contract

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/v1/customers` | Create a customer |
| GET | `/api/v1/customers/{customerId}` | Retrieve a customer |
| POST | `/api/v1/accounts` | Open an account for an existing customer |
| GET | `/api/v1/accounts/{accountId}` | Retrieve an account |
| GET | `/api/v1/accounts/{accountId}/balance` | Retrieve the account balance projection |

Request/response examples are in `docs/phase-1-api-examples.md`.

## 1.4 Test preparation

Start PostgreSQL and the application:

```powershell
docker compose up -d postgres
mvn clean test
mvn spring-boot:run
```

Use unique email addresses for each run, for example `phase1.<timestamp>@example.test`. Save the returned `customerId` and `accountId` for subsequent requests.

## 1.5 Scenario A — Customer creation and retrieval

1. Send `POST /api/v1/customers` with valid first name, last name, email and phone number.
2. Expected: HTTP `201 Created`; response contains the generated customer identifier and normalized email.
3. Repeat with the same email using different letter casing and/or surrounding whitespace.
4. Expected: HTTP `409 Conflict` for the duplicate normalized email.
5. Send `GET /api/v1/customers/{customerId}` using the returned ID.
6. Expected: HTTP `200 OK` and the same customer identity.
7. Use a syntactically valid but unknown UUID.
8. Expected: HTTP `404 Not Found`.

## 1.6 Scenario B — Account opening and balance

1. Open a SAVINGS account for the ACTIVE customer with currency `MYR`.
2. Expected: HTTP `201 Created`; account number is server-generated; balance is `0.0000`; status is `ACTIVE`.
3. Retrieve the account using `GET /api/v1/accounts/{accountId}`.
4. Expected: HTTP `200 OK`; owner, account type, currency and status match the creation response.
5. Retrieve `GET /api/v1/accounts/{accountId}/balance`.
6. Expected: HTTP `200 OK`; balance is zero and currency is MYR.
7. Attempt to open an account for an unknown customer.
8. Expected: HTTP `404 Not Found`.
9. Attempt to open an account for a customer whose status is not ACTIVE, if the test fixture supports that state.
10. Expected: HTTP `422 Unprocessable Entity` according to the current Phase 1 contract.

## 1.7 Scenario C — Request validation

Exercise missing required fields, malformed email, invalid account type, invalid currency and malformed UUID values.

Expected: invalid request fields return HTTP `400 Bad Request` with the common validation error contract where wired. An unknown resource remains a 404 rather than being reported as a validation failure.

## 1.8 Database verification

Verify customer and account records:

```sql
SELECT id, first_name, last_name, email, phone_number, status, created_at, updated_at
FROM customers
ORDER BY created_at DESC
LIMIT 20;

SELECT id, customer_id, account_number, account_type, currency, balance, status,
       created_at, updated_at
FROM accounts
ORDER BY created_at DESC
LIMIT 20;
```

Verify that newly opened accounts have zero balances:

```sql
SELECT id, account_number, balance, currency
FROM accounts
WHERE balance <> 0;
```

For a newly initialized Phase 1 database, this query should return no rows unless test data was deliberately changed by a later phase's local test setup.

## 1.9 Automated verification

```powershell
mvn clean test
```

Review the test summary and ensure the customer, account, validation and journal-validator tests pass. Do not treat a successful application startup as a substitute for the automated test suite.

## 1.10 Pass condition

Valid customers and accounts can be created and retrieved; duplicate emails, invalid requests and missing resources produce the documented errors; new accounts begin at zero; and the journal validator rejects invalid or unbalanced journals.
